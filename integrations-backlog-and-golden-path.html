External interfaces backlog, and the one flow that has to work on mocks alone

Two different questions, answered separately on purpose. §1 is everything that eventually needs a real vendor behind it — a backlog for Spec Kit to pick up one integration at a time. §2 assumes you never flip a single one of those on, and asks: what's missing to make one continuous walkthrough — admin → tutor → student → parent — actually click together today, fully mocked. The short answer to §2 turned out better than expected: most of it already works. The gaps are specific and small.

Numbering correction: specs/007-sessions-timetable already exists (status Testing, not yet Accepted) — it added `sessions` + `availability` screens, taking the closed catalog from 47 to 49 ids, and gave every session a computed display_status (Upcoming / Auto completed / Staff completed / Cancelled). That's exactly the "was this class actually delivered" signal the earlier hourly-billing plan needed and assumed was missing. Next open spec slot is 008, not 007.

2 One coherent mocked flow across admin, tutor, student, parent

Audited by reading the actual wired screens and routers (not assumed): frontend/components/wired/{Join,LiveTeacher,LiveStudent,SessionVideo,Record,Billing,Payments}Screen.tsx and the endpoints they call.

What already works, verified: Join → live-teacher/live-student → record → timeline write is real, not placeholder — each screen calls a real endpoint and changes real state (/join/{token}, /join/{token}/enter, /sessions/{id}/live, /sessions/{id}/engagement, /sessions/{id}/record). Billing has a real "Issue invoice" form (owner-only, POST /invoices) with a plan-driven auto path through auto_invoice(). Payments has a real "Pay (mock)" button wired to POST /payments/checkout, ownership-checked. Parent fee visibility defaults to visible once a link is accepted — it does not silently hide invoices. Role gating is more permissive than the catalog's single `role` field suggests: parent already reaches payments/timeline/reports/messages through the student/faculty routes via multi-role `LoginGate`. "Faculty" is confirmed a display label only — the real RBAC role is `teacher`.

Punch list — minimal, 100% mock, no vendor work

  1. Run the walkthrough live, once, in a browser. Everything above was verified by reading source, not by clicking. This is the single highest-value next step and the only way to catch the sessions[0] fallback risk. I can drive this myself in the built-in browser pane against your local dev stack (Compose Postgres + uvicorn + npm run dev) if you want it done now, as admin → teacher → student → parent, back to back.
  2. Add backend/tests/test_walkthrough.py — one integration test chaining workspace → roster → cohort → schedule → join/enter → record → timeline assertion → invoice(auto) → checkout → invoices/mine paid for both student and accepted parent. Turns "should work" into "proven to work," and catches the next regression before a live demo does.
  3. Default auto=true in BillingScreen.tsx when a plan is picked so the first click in any demo is plan-accurate, not a placeholder number.
  4. Write down the parent-link hand-off as an explicit demo step (mint token as staff, paste as parent) — no code change, just avoids a confused pause mid-walkthrough.

None of this needs a spec-kit feature on its own — items 2–4 are small enough to fold into whichever spec picks up the billing work (see billing-subscription-plan.html §5), and item 1 is just running what already exists.
