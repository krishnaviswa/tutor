Subscriptions, billing, payments & history — what's really needed

TutorOS already has three billing-shaped screens (billing, payments, subscription, payouts) and a real proration/coupon engine — but it's one flat-plan model with no recurring engine, no ledger, and no usage-based billing. This plan covers (1) the two billing axes end-to-end, (2) the new static-vs-hourly cohort billing mode, and (3) what's required beyond billing for this to be a real public product. No new screen ids anywhere below — every change extends an existing one.

0 The two billing axes, today

TutorOS is two-sided: the platform charges the tenant (workspace), and the tenant charges its students/parents. They're easy to conflate — they aren't the same invoice, plan, or port.

3 Static vs. hourly billing, chosen per cohort the core new requirement

Today Plan is flat-only (amount_cents + interval). There is no rate concept, no duration field, and no billing-mode toggle anywhere in the schema.

What exists
  • ScheduledSession.status: scheduled/completed/cancelled — the gate for "did the class happen"
  • ends_at exists but is nullable — duration isn't reliably captured
  • Attendance.status: present/absent, one row per student per session
  • Zero occurrences of hourly / rate_card / billing_mode anywhere in the codebase
Design decision
  • Cohort.billing_mode: enum static | hourly, default static — lives on Cohort, matching "chosen per cohort"
  • Cohort.rate_cents: nullable per-hour rate — no separate rate_cards table until per-teacher overrides are actually needed
  • No per-subject rate (would break subject-neutrality, non-negotiable #1)

6 What's actually required before this goes public

Billing is one gap among several. The app is "half-baked" in the sense that every business flow is currently simulated against mock ports by design (README §1) — that's correct for local dev, but each of these needs a deliberate decision before a real user's money, data, or class time touches it.

Payments & money (P0)

  • Real gateway integration behind payments_student/payments_platform ports (Razorpay is the natural fit given WhatsApp/India context) — webhooks, signature verification, retries
  • PCI scope stays with the gateway (hosted checkout/tokenization) — never store card data
  • Refund, dispute/chargeback handling; reconciliation report (gateway settlement vs. internal ledger)
  • GST/tax invoicing if operating in India; VAT/sales-tax elsewhere
  • Payouts to teachers: real bank transfer rail + KYC/PAN collection, not a status field

Auth & identity (P0)

  • Replace OTP stub (000000) with a real SMS/OTP or WhatsApp OTP provider
  • Real magic-link email delivery, rate-limited
  • Session/token hardening: refresh rotation, device/session revoke, brute-force lockout

Data protection & compliance (P0)

  • PII handling for minors (most students) — consent, parental controls, data retention/export/delete (India DPDP Act / GDPR if applicable)
  • Tenant data isolation testing beyond unit tests (pen-test the workspace_id boundary)
  • Secrets management for vendor keys (no .env in prod; use a vault)
  • Encryption at rest for Postgres in the hosted environment; backups + tested restore + DR runbook

Vendor ports going live (P1)

  • Meet/Teams calendar_video: real OAuth + link generation, not mock join URLs
  • WhatsApp Business API (Meta) — template approval, opt-in/opt-out compliance, rate limits
  • Object storage (S3-compatible) for recordings/attachments, signed URLs, retention policy

Operability (P1)

  • Structured logging, error tracking (Sentry-class), uptime/latency monitoring, alerting on payment failures specifically
  • Load/perf testing once real traffic is expected — QuotaGuard today throttles logical usage, not infra load
  • Staging environment with production-shaped (but fake) data for pre-release checks

Support & ops tooling (P2)

  • Admin console for support staff to inspect/refund/re-send without direct DB access
  • Customer support channel + escalation path for billing disputes
  • Status page / incident comms

Legal (P0 before charging anyone)

  • Terms of Service, Refund/Cancellation Policy, Privacy Policy published and linked from checkout
  • Entity/GST registration for the operating business, if applicable
  • Data processing agreements with each vendor (gateway, WhatsApp/Meta, hosting, storage)

None of this is TutorOS-specific engineering debt — it's the standard gap between "mock-port simulation, correctly scoped for a local dev spine" and "product a stranger can pay for." The billing work in §1–§3 is the right next spec; the rest becomes real work items once a hosting target and payment provider are chosen.
